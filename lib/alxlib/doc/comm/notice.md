# alxcomm — Known Limits and Pitfalls

Boundary cases and pitfalls that are **outside the behaviour contract but not counted as defects**. Each entry gives its trigger and its check.

## HTTP

- **A peer-declared size has a hard cap (64 MiB, no API knob)**: on the server a `Content-Length` past the cap drops the receive cache, and that request is neither handled nor answered (the peer notices through its timeout, there is no 413); on the client a chunked block past the cap fails outright, while the accumulated body still grows with `m_buffer`.
- **chunked decoding does not support chunk extensions**: a block-length line carrying `;ext` fails outright (`decode_chunked` calls it a format error), and the trailer section is ignored. A peer that uses extensions (rare) is judged illegal.
- **The connection is not reset after a send failure**: when `send_data` returns false on an `SO_SNDTIMEO` (5s) timeout or an error it **may already have written part of the data**, while the socket stays valid and `connect_num()` still reads 1 -- the upper layer's next message continues on a half-written stream, the peer can no longer find the boundary, and it may take the tail of the previous reply for the answer to a new request. `tcp_server` already does `close(key)` to kick that peer out on a failed send; `tcp_client` / `local_client` / `local_server` / `tls_client` / `tls_server` do not. The HTTP client therefore does **not** void the in-flight request on a send failure: `exec()` returning true only means the request was queued, a failure only reports on `mesg_prit`, and the timeout is the host's to handle (contract). Check: `bytes_send` returns false while `connect_num() != 0` (the trigger takes a stall on the order of "the peer does not read for 5s"). Judged true but narrow on 2026-09-24; per "comm does not chase completeness" it is recorded, not fixed.
- **HTTP client: the narrow window where `exec()` interleaves with a disconnect event**: the host calls `exec()` in the middle of handling a disconnect in `on_trans_event` (the previous future has just landed and it re-sends at once), and the new request's promise may be landed by that same voiding while its bytes have already gone into the send queue -- they go out after the reconnect, and the reply is either dropped as "no request in flight" or lands on the host's next request (a silent wrong answer). The window is between the two steps "clear the queue" and "void"; the trigger needs the host to re-send at exactly that moment. Fixing it takes a lock, and per "contract over foolproofing" it is not fixed.

- **A re-send right after a successful reply wakes the caller may be refused by mistake**: the tail of `client::on_bytes_recv` is `m_promise->set_value(...)` followed by `safe_delete(m_promise)` (`source/alxcomm/ahttp.cpp:681-683`; `abort_pending()` does the two in the opposite order and is right), so a caller woken by the future that calls `exec()` again at once reads `m_promise` as still non-null and gets false -- it is told "a request is already in flight" when there is none. The window is two statements long, and the trigger needs the host to re-send on the very instant the answer lands. Check: a second `exec()` right after an `exec()` that has just returned (`wait_for(0s)` just ready). Recorded 2026-09-26, code unchanged.

## TLS

- **The first `open()` ignores `SIGPIPE` process-wide**: it sets `SIG_IGN` only while the process's current `SIGPIPE` is `SIG_DFL` (a host-installed handler is left alone). Reason: OpenSSL sends alerts and records through a bare `write()`, so a peer that disconnects gets the process a `SIGPIPE` and kills it (plain TCP avoids this with `MSG_NOSIGNAL`, the TLS path has none). This is a **process-wide side effect**; a host that relies on the default disposition has to restore it itself.
- **Configuring `ca` forces a `hostname`**: a missing `hostname` refuses the connection outright, with no fallback to "chain verification only". `hostname` accepts a DNS name or an IP literal (the latter goes through `set1_ip_asc`), and the check carries `NO_PARTIAL_WILDCARDS`. Without a `ca` the peer identity is not verified.
- **The TLS server is still one thread per connection**: the handshake has moved off the accept thread (it no longer blocks the connections behind it), but the ceiling on connections is still the thread count. The handshake has a 10s timeout (`SO_RCVTIMEO`), and a timeout ends as a handshake failure.
- **The send timeout is a 5s `SO_SNDTIMEO` (one send call)**: with a peer that reads nothing at all, sending a large message returns a failure after a few timeout periods, and **may already have written part of the data**. The TLS path carries an extra `steady_clock`-based "no progress" bound on top. Measured order of magnitude: a 32 MiB message to a peer that never reads makes close return in about 15s; a "cumulative deadline" version (about 4.5s) was tried but would kill legitimate slow transfers of large packs, so it was not adopted.

## Memory

- **An OOM on one of the library's own threads terminates**: an allocation in `bytes` throws `std::bad_alloc` / `std::length_error` (see `doc/base/design.md` §1.4), and the send and receive threads of `comm` are `std::thread` entry functions -- an exception that escapes them is `std::terminate` (the whole process dies, without going through the host's error path). Per the rule "no fallback for a non-hot path" it is **not** caught, only recorded here.

## Send and receive model

- **All sends are serialized in one worker thread**: a peer that does not read slows down the sends to every other peer (it no longer blocks them forever); curing that needs a per-connection send queue or thread.
- **The connection is not reset after a streaming send failure**: when `send_data` returns false on an `SO_SNDTIMEO` (5s) timeout or an error it **may already have written part of the data**, while the socket stays valid and `connect_num()` still reads 1 -- the upper layer's next message continues on a half-written stream, the peer can no longer find the boundary, and it may take the tail of the previous reply for the answer to a new request. `tcp_server` already does `close(key)` to kick that peer out on a failed send; `tcp_client` / `local_client` / `local_server` / `tls_client` / `tls_server` do not. Check: `bytes_send` returns false while `connect_num() != 0` (the trigger needs "the peer stops reading for 5s and the message is larger than the buffer"). Judged true but narrow on 2026-09-24; per "comm does not chase completeness" it is recorded, not fixed.
- **A transport handed to a `comm`-derived object must not have been `open()`ed by the host first**: `transmit` is owned by `~comm()` (the destructor does the `delete`), and the switch is driven only by the session layer's `open()` / `close()`. When the host opens it itself and then hands it over, `comm::close(0)` returns at once because "the session is not open" and never closes the transport, so that receive thread outlives the host object's members (callbacks land in an already-destroyed derived object). Check: the transport that `client(transmit*)` is handed already reports `is_open()` true while the host never calls `client::open()`. Also a use outside the contract; recorded only.
- **`bytes_send` returns success while every connection is still handshaking**: the semantics are "having no peer to send to is not a failure", so a caller cannot conclude from that return that the data really went out (check: it returns true directly when `ready_count == 0`).
- **`rpc::list_service()` now holds the service-table lock**: it serializes with `install_service` / `remove_service`; `on_exec_service` takes a copy outside the lock and runs there, so it cannot self-lock.

## Transport layer

- **`transmit::from_strip` returns `{0, 0}` for every out-of-bounds input**: a segment > 255, a port > 65535, an empty segment (`1..2.3:80`) or an over-long number all return `{0,0}` instead of throwing; `isdigit` has been given its `(unsigned char)` cast.
- **`send_data` treats a `send` return of 0 as a failure**: to avoid the `offset += 0` infinite loop.
- **`wsa_utils::io_interrupted` only judges `EINTR` / `WSAEINTR`**: every other error (including `EAGAIN`) takes the failure path, so the caller has to tell "failed on a timeout" from "a real error" itself.

## Packing and RPC

- **The packing protocol's `version` field is written and never checked**: `pack_head.ctrl.version` is written as a fixed `0x00000001` on the encoding side (`source/alxcomm/acomm_ex.cpp:107`) and never read on the decoding side (the whole tree has only the definition and that one write), so a peer that changes the layout is not stopped by the version -- only the checksum (over the payload) of `is_verify()` may catch it. Check: change the written value and the parse result is unchanged. Recorded 2026-09-26, code unchanged.
- **Losing sync and clearing the whole cache drops a half marker with it**: when `packer::append()` cannot find `_PACK_HEAD_` it `clear()`s the entire cache (the "no pack head in cache, drop all!" in `acomm_ex.cpp`), and a half marker within the last 8 bytes is dropped along with it; unreachable on a clean stream (the cache always holds a whole marker before the loop is entered), so it is a narrow boundary reached only after losing sync.
