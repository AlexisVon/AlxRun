# alxcore — Known Limits and Pitfalls

Edge cases and pitfalls that are **outside the behavioural contract and not counted as defects**. Every entry gives its trigger and its check.

## Encryption and compression

- **The AES padding semantics changed, so old ciphertext is not guaranteed to unpad under the new rules**: `ANSIX923` and `ISO10126` now **always** append a whole block, an already aligned buffer included, and unpadding accepts `pad_len == 16` accordingly. The old version appended nothing when the buffer was aligned, so the last byte of old ciphertext is data itself; unpadding it under the new rules may strip 1..16 bytes too many. Check: the old implementation was not self-consistent (it appended nothing yet stripped by the last byte, so any last byte below 16 was mis-stripped), and there is no old format worth migrating, so no compatibility is attempted.
- **`decoder_gzip` caps its output at 1 GiB**: the buffer starts at `min(compressed size * 4, 1 GiB)`, and reaching that cap fails the whole call (an empty `bytes` is returned) rather than succeeding truncated -- a small input may not expand without bound.
- **The size clamp in `decoder_lz4` is forgery defence, not a limit on legitimate sizes**: both `sexec` and `exec` clamp the claimed original size to `min(claim, compressed length * 255 + 16)`. That bound is LZ4's worst-case expansion (255 bytes out per input byte at most), so a legitimate stream's claim always falls inside it; a claim that really is above the bound is clamped to it and finally judged wrong by the caller's own size check (the symptom is a failed decode). Without this layer the same forged claim on `exec` forced a 2 GiB virtual reservation (measured VmPeak +2097156 KB) while `sexec` used only ≈6.5 KB (the 26-byte compressed stream of that case gives `26*255+16 = 6646 B`) -- the two paths have to give the same answer.
- **zstd frames carry no content checksum** (the zstd library default `ZSTD_c_checksumFlag = 0`, never turned on): decoding detects **structural** damage (a bad block header, a length that does not add up, an incomplete frame), but **a change in the payload is not guaranteed to be detected** -- measured, flipping one byte in the middle of a compressed body can decode to content of the same length that differs. Check: this is the same property as lz4 (a bare block carries no checksum), and integrity is the outer layer's job (`afpacker`'s CRC / the caller's hash); turning the checksum on adds 4 bytes per frame and one more pass over the data, so whether it is worth it is the user's call. `gt_acompress.zstd_rejects_bad_input` pins this boundary as "either it fails, or the result differs".
- **`afpacker` reuses the key stream across two archives** (`source/alxcore/afpacker.cpp:153-154` / `:253` / `:290`): the IV is the pair (compressed length, offset in the archive) and the key is a single `SHA-256(pswd)`. Under one key, if two archives hold the same two values in one slot, key+IV are the same → the key stream is reused: **the ciphertext of that slot is byte-for-byte identical**, so a byte-by-byte comparison locates "which ranges of the two archives agree" (it yields neither content, nor fields, nor block boundaries -- the index in ciphertext form is a compressed stream, an XOR of the two is noise, and a change shifts the literal/match split as a whole).
  **Verdict: by design, not counted as a defect** -- CTR's uniqueness requirement is on the key, not on a single archive, and "a unique key per archive" (salting / a slow hash) is the shell's job; `afpacker` promises nothing there, and the bar is not lowered as long as the key does not leak. The model, the premises and every boundary are in `design.md` §5.4. Should this be changed later, the header's `aes_flag` slot can take a new value (say `FILE_AES2`) for the new scheme while old archives stay readable as `FILE_AESC`, with no version number and no format break.

## Image

- **`create_image` refuses a giant size declared by a header**: `h * line_bytes` above 1 GiB returns `nullptr`; the check is written as a division (`line_bytes > 1 GiB / h`), since the multiplication form would fail through `uint_64` wraparound at extreme widths and heights.
- **`load_image_bmp` now requires `ofst + dsize` to equal the total data length exactly**: the check went from the old code's one-sided comparison (`<`) to equality. A BMP with trailing padding or appended data is judged invalid and returns `nullptr`.

## File and IO

- **`file::write` advances the cached size to `max(FTELL, the size it held)`**: after a write `file_info::size()` reflects the new length at once; `file::open(WRIT / WRIT|R__W)` sets the size to 0 explicitly (truncation semantics).
- **`file::read_all` reads to EOF and does not trust `st_size`**: procfs reports 0 bytes yet often has content, a FIFO cannot be seeked at all, and both are read in full as a stream; the size only hints at the capacity to preallocate. `_ok` reports what happened -- **an empty file is `true` too**, and only an open or a read that failed gives `false`.
- **`file::read` is a positional read, and holds only on a seekable source**: on a FIFO/socket/tty it gives `ok=false` and an empty buffer (the old behaviour was an empty buffer in silence); read such a source with `read_all`.
- **`file::flush()` returns what `fflush` decided** (the old signature was `void`): `false` means the buffered data did not reach the disk.
- **`ostream_file::reset()` reopens with the mode the constructor was given**: an append stream keeps appending, a non-append stream restarts truncated; `reset()` does not change `open_type_`.
- **`exec_sync` runs the child in its own process group, and the timeout `SIGTERM`s that whole group**: `kill(-pid, SIGTERM)` takes down the child together with anything that inherited its pipe write end, so no process is left holding the pipe. The signal is a `SIGTERM` and nothing escalates to `SIGKILL`, so a process that ignores it keeps running; the call reports `timeout = true` either way.

## Threads and concurrency

- **`threadpool(0, 0)` is clamped to 1 thread + 1 queue slot**: neither `_threads == 0` nor `_queue_limit == 0` produces a "dead pool with zero workers" any more.
- **A logger `queue_limit` of 0 (or the key absent) is clamped to 1024**: an async logger's producers would otherwise block for good.
- **`safe_queue::destroy()` and `reset()` set the flag and drain the queue inside one critical section**, and the `notify` sits outside the lock: after `destroy()` both `block_push` and `block_pop` return `false` at once, and no wakeup is lost.

## Process

- **`process_info::path` is the resolved real executable, not the name it was started under**: when a symlink (or a hard link) started the process, `readlink /proc/<pid>/exe` gives the target file while `comm` is the start name. `find_process(name)` therefore matches on `basename(path)`, which differs from matching on `comm` -- the point being that a process cannot disguise itself as another program with `PR_SET_NAME`.
- **A `path` that cannot be read is empty**: a POSIX kernel thread has no executable (`/proc/<pid>/exe` does not exist) and reading another user's process may be held back by ptrace permission; a restricted or system process on Windows fails `OpenProcess`. Such a process has an empty `path` and `find_process(name)` cannot match it either, so the host handles the empty case itself. After the exe has been deleted or replaced, the path `readlink` returns **carries its `" (deleted)"` tail as it stands**; the library does not strip it.
- **The `comm` in `/proc/<pid>/stat` may hold spaces, right brackets and newlines** (writing `/proc/self/comm` does not strip a trailing newline, so a bare newline turns up in the stat line). This file therefore **cannot be read line by line**: the library reads it whole and parses the fields after the **last** `')'` as the anchor. Check: for a process that ran `echo 'my prog' > /proc/self/comm`, the implementation this replaced threw `std::invalid_argument` or dropped the whole entry.
- **By the time `start()` returns the child has already `exec`-ed**: the POSIX side synchronizes that step with a status pipe (a `CLOEXEC` write end plus the parent reading EOF), and Windows' `CreateProcessA` is synchronous to begin with. So `find_process(ctrl.pid())` right after `start()` finds **the child's** identity, no longer a mirror of the parent.
- **A Windows abnormal exit code appears as a negative number**: the `DWORD` `GetExitCodeProcess` gives (an access violation `0xC0000005`, say) comes out of the `(int_32)` conversion negative (`-1073741819`); on POSIX "killed by a signal" goes through `signaled` + `term_sig` and `exit_code` stays `-1`. Judging whether it crashed means looking at each platform on its own terms.
- **Both `loop()` implementations know EOF now**: on Windows a `ReadFile` reporting `ERROR_BROKEN_PIPE` / `ERROR_HANDLE_EOF` (or reading 0 bytes) ends that pipe, and once both have ended the loop exits and sets `output_done()`; the POSIX side always exited on the two pipes' EOF. The only difference is who holds the pipe write end -- the loop stops only when the child has exited and no descendant inherited the write end; if one did, both platforms have to wait for it.
- **Output may not be fully delivered when `wait()` / `status()` return**: what they wait for is the child being taken by `waitpid`, while the `loop()` thread is still handing over the bytes left in the pipes block by block (one stdout read per round plus one 10 ms `select` timeout for stderr), so a tail of ten thousand bytes takes tens of milliseconds. Reading the accumulated output then sees half of it, and **releasing the handle (`kill()` / destruction) at that moment loses the remaining blocks for good** -- the natural-exit path is the same, `kill()` is not the only way to lose them. Check: read, and release, only once `output_done()` is true.
- **The Windows build goes through the A-version APIs ⇒ narrow strings are read in the system ANSI code page** (not UTF-8): UTF-8 requires the host exe's manifest to declare `<activeCodePage>UTF-8</activeCodePage>` (Win10 1903+), and the library introduces no manifest. This matches the existing stance of `file` / `file_info`.
- **`RLIMIT_AS` does not stop `exec`**: the POSIX memory wall governs "the allocations the child makes once it runs", not "whether it can be started" -- measured, `RLIMIT_AS=1` still `exec`s successfully, the program that comes up simply dies of a failed allocation of its own later (a shell under `RLIMIT_AS=8MiB` runs normally and reads back 8192). Check: under a 64 MiB wall a 128 MiB allocation inside the child fails (the no-wall control group succeeds).
- **The two platforms' memory walls are not the same thing**: on POSIX `mem_bytes` is `RLIMIT_AS` (**address space**, mapped but uncommitted parts included), on Windows it is the job object's `JOB_OBJECT_LIMIT_PROCESS_MEMORY` (**commit**). One number holds back different things on the two sides; do not treat them as equivalents.
- **A Windows job covers the whole descendant tree**: the limits apply to the child and its descendants, and closing the job handle in `kill()` / destruction kills everything left in the tree (`KILL_ON_JOB_CLOSE`). If this process is itself inside a job already (the common case when an IDE or CI started it), attaching a new one needs the nested jobs of Win8+, and a failure to attach returns `false`, fail-closed.
- **One `process_ctrl` instance belongs to one calling thread**: `status()` / `wait()` / `kill()` / `input()` are not mutually excluded; separate instances may run concurrently freely. The exception is `output_done()` -- it is an atomic inside, so another thread may read it (the `loop()` thread writes it). Also, `kill()` / destruction join the `loop()` thread, so a signal callback must not wait on a lock the calling thread holds.

## Regex

- **One `regex_pcre2` instance is one matcher: not copyable, its functions do not run concurrently**. No two methods on one instance (the `const` ones `find` / `find_all` / `is_compliant` / `replace` / `match_group` included) may run at the same time -- the match block and `last_status()` / `last_error_code()` are unique to the instance; `set_callout` / `set_step_limit` / `set_depth_limit` / `set_substitute_options` may not run concurrently with a match either (the first three write the match context, and `set_callout` concurrent with a match is a **use-after-free**: it frees the old binding, and that is what the bridge of the match in flight reads). The callout and its `ud` belong to that instance **alone**: for parallel work, **construct one instance per thread** with its own hook rather than sharing one object, and do not count on copying one either (the reasons copying was rejected: inheriting the hook = two matchers sharing one stop signal, not inheriting it = a silent difference between the original and the copy). **The library adds no lock and does no detection**: violating the constraints above is not caught (it is a data race), and the caller guarantees them. Compare `regex_ex`, which is copyable the other way round and `const`-read-only shareable, with none of these constraints.
- **On failure `replace` / `replace_all` return their argument unchanged**: no throw, and no empty string either. The reason is in `last_status() == error` (`last_error_code()` gives PCRE2's own negative code) -- not looking at the status turns "it errored" into "it did not match".
- **The replacement string is PCRE2's dialect**: `$12` is group 12 (and fails the call with the subject returned unchanged when there is no such group), not ECMAScript's "group 1 plus a literal 2", which PCRE2 spells `${1}2`. A group that took no part substitutes an empty string by default (`PCRE2_SUBSTITUTE_UNSET_EMPTY` is on by default and `set_substitute_options()` can change that).
- **The default step cap is 10⁷ steps** (PCRE2's factory default, measured ≈ 0.14 s on this machine; the depth cap defaults to the same value): there is a ceiling even with none set; lower it for a shorter wall-clock bound.
- **The export table of `bin/libalxcore.so` carries third-party symbols** (measured; `pcre2_*` and the zlib / lz4 / sqlite3 symbols leak the same way, a pre-existing property rather than something introduced here): the static archive's symbols are not hidden, so a host that links another PCRE2 into the same process may be preempted. The fix is `--exclude-libs,ALL` at link time, a decision for the whole module, left alone here.

## Platform and other

- **The POSIX and Windows fibres are not fully aligned in semantics**: the POSIX side ignores `_reserve_size` (only the `commit > reserve` check survives), uses a 1 MB default stack, puts one `PROT_NONE` guard page at the bottom of the stack, and allocates the stack with `mmap`/`munmap`; the Windows side lets `CreateFiberEx` allocate by commit/reserve and grow it automatically.
- **`sqlite::stmt` holds a bare `sqlite*` only**: when the `sqlite` object is destroyed before the `stmt`, `stmt::last_error()` dereferences a dangling pointer (`sqlite3_errmsg(NULL)` itself is safe, but `db_` is already gone). `sqlite::close()` uses `sqlite3_close_v2`, so with statements not yet finalized the connection turns into a zombie and is released once the statements are destroyed.
- **`sqlite::stmt::get_text` returns an empty string for a NULL column**: a NULL column no longer goes through constructing a `std::string` from `(const char*)nullptr` (UB) and returns `std::string()`; text with embedded NULs comes back at the full length `sqlite3_column_bytes` reports.
- **`mmap::set` / `MMAP_PROTECT` check bounds by subtraction**: `_offset > size` or `_size > size - offset` returns `false` in every case, with no `uint_32` wraparound in an addition.
